Boundaries — the refusals are part of the design

Honest fallback — no matching script

A child afraid of the dark at bedtime: no approved Appendix B script matches this situation. The Lab says so plainly instead of inventing one, and points the parent back to the Wheel.

Ambiguous fallback — signals point two ways

One scenario carries signals for two different approved scripts. Rather than guess, the Lab stops and lets the parent choose the focus on the Wheel first.

Invalid proposal — validation rejects it

A mock model proposal invents a Cycle stage that does not exist in the published framework. Deterministic validation rejects the proposal in full — it is never repaired or shown as guidance.

Safety stop — the model is never called

A fictional safety test (scenario D-01): a self-harm disclosure. Deterministic screening stops the run before any model call — 0 model calls — and shows the approved safety wording. A safety stop cannot be confirmed away, retried around, or overridden.

How to read the labels

LIVE — a real model response, produced in the moment. This demonstration never runs live.

RECORDED LIVE — a genuine live model response, recorded earlier and replayed verbatim. Only the AT1 proposal carries this label (Muse Spark 1.3 Standard, recorded Oct 26, 2026).

MOCK — a demo stand-in written for this page; it stands in for the live model so the deterministic system around it can be inspected.

FALLBACK — the system declined to offer a script: no match, an ambiguous match, or a rejected proposal. A fallback is an honest refusal, not an error.
